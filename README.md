# Практики, не имеющие привязанности к конкретным проектам





## Описание
В данном репозитории представлены практики, выполняемые в ходе курса `Фулстек-разработка`, 
которые выполнялись только ради ознакомления с материалом 
(не использовались для реализации проектов). Методические указания и теоретический материал 
к практикам находятся в папках `files-backend/` для `бэкенд разработки` и `files-frontend/` для `фронтенд разработки` 





## Бэкенд разработка
### HelpDesk
#### Цель работы
Научиться строить `Minimal API`, которое корректно обрабатывает исключения и `HTTP-ошибки`, возвращает разные типы ответов через Results `API` и использует собственный `IResult`. 
#### Сквозной сценарий задания
Необходимо создать веб-приложение `HelpDesk.Results`. Это учебный сервис заявок в службу поддержки. Приложение должно показывать список заявок, возвращать данные в разных форматах, обрабатывать ошибочные запросы имитировать серверное исключение, отдавать файл-инструкцию и демонстрировать разные способы формирования `HTTP-ответа` через `Results API`. 
#### Обязательные маршруты и ожидаемое поведение 
| Запрос | Ожидаемое поведение  | Какая тема проверяется  |
| - | - | - |
| /  | Главная `HTML-страница` с кратким описанием проекта и ссылками на тестовые маршруты. Должна быть сформирована через собственный `IResult`.  | `Custom IResult ` |
| /about/text | Возвращает простой текст через `Results.Text(...)`.  | `Text result ` |
| /about/content  | Возвращает текст через `Results.Content(...)` с явно заданным `MIME-типом` и кодировкой.  | `Content result ` |
| /api/tickets  | Возвращает список заявок в `JSON`.  | `Json` / `Ok`  |
| /api/tickets/1 | Возвращает найденную заявку со статусом 200.  | Ok + маршрут с параметром  |
| /api/tickets/999  | Если заявки нет, возвращает 404 и сообщение. | `NotFound` |
| /api/tickets/create?title=Printer&priority=2  | Создает учебную заявку и возвращает `201` или `200` с данными созданной заявки.  | `Created` / `Ok` + `Json`  |
| /api/tickets/create?priority=2 | Без `title` возвращает `400` с объяснением ошибки.  | `BadRequest` |
| /status/unauthorized | Возвращает `401`.  | `Unauthorized` |
| /status/forbidden | Возвращает `403` через `Results.StatusCode(403)` или эквивалентный результат.  | `StatusCode` |
| /status/custom/418  | Возвращает произвольный статус-код `418` через `Results.StatusCode(...)`. | StatusCode |
| /redirect/old-tickets  | Выполняет локальную переадресацию на `/api/tickets`. | `LocalRedirect` |
| /redirect/ticket/1 | Выполняет переадресацию на именованный маршрут заявки.  | `RedirectToRoute`  |
| /files/readme | Отдает файл `readme.txt` с корректным `Content-Type` и именем загрузки.  | `File result` |
| /throw  | Генерирует исключение для проверки `UseExceptionHandler` / `DeveloperExceptionPage`. | `Exception handling` |
| /unknown | Возвращает `404` с понятным текстом или `JSON`, а не пустую страницу. | `StatusCodePages` |

#### Требования к построению pipeline
- Middleware обработки исключений должен быть подключен ближе к началу `pipeline`, до маршрутов, которые могут выбросить исключение. 
- `UseStatusCodePagesWithReExecute(...)` или `UseStatusCodePages(...)` должен быть подключен до конечных точек, чтобы обработать `404`/`401`/`403`, у которых еще нет тела ответа. 
- Маршруты `/error/exception` и `/error/status/{code:int}` не должны сами генерировать исключения или создавать циклическую переадресацию. 
- Если используется `UseStatusCodePagesWithRedirects(...)`, студент должен объяснить, почему клиент получает `302`. В основной реализации предпочтительнее `ReExecute`, потому что исходный статус сохраняется. 
- Нельзя отправлять технические детали исключения пользователю в `Production: stack trace`, имена внутренних классов и абсолютные пути не должны попадать в ответ. 
- Нельзя формировать `redirect` на внешний `URL` из пользовательского `query-параметра` без проверки. В этой работе достаточно локальных переадресаций. 
- Файл для `Results.File(...)` должен находиться в заранее известном каталоге. Не принимать произвольный путь к файлу из запроса. 
#### Отдельные задания по обработке ошибок 
1. Проверить `/throw` в `Development`. В отчете описать почему такая страница полезна разработчику, но неприемлема для пользователя. 
2. Проверить `/throw` в `Production` или описать, как переключить среду через `launchSettings.json` / переменные окружения. Ответ должен быть `500` без технических деталей. 
3. Проверить `/unknown`. Ответ должен содержать статус `404` и понятное сообщение. 
4. Проверить `/status/unauthorized` и `/status/forbidden`. Ответы должны иметь статус `401` и `403` соответственно. 
5. В отчете объяснить, чем исключение отличается от `HTTP-ошибки`: исключение возникает внутри кода, а `HTTP-ошибк`а может быть штатным результатом обработки запроса. 
#### Отдельные задания по Results API
1. Использовать `Results.Text(...)` и `Results.Content(...)`, причем во втором случае явно задать тип содержимого и кодировку. 
2. Использовать `Results.Json(...)` или `Results.Ok(...)` для выдачи списка заявок и одной заявки. 
3. Использовать `Results.BadRequest(...)` для некорректного запроса создания заявки. 
4. Использовать `Results.NotFound(...)` для несуществующего `id`. 
5. Использовать `Results.Unauthorized(...)` и `Results.StatusCode(...)` минимум на двух отдельных маршрутах. 
6. Использовать `Results.LocalRedirect(...)` и `Results.RedirectToRoute(...)`. 
7. Использовать `Results.File(...)` для отдачи файла `readme.txt`. 
8. Создать свой `HtmlResult` и использовать его хотя бы в одном `endpoint`. 




### CampusHub.ConfigCenter
#### Цель работы
Научиться собирать конфигурацию `ASP.NET` Core из нескольких источников, анализировать секции, создавать собственный провайдер конфигурации, связывать данные конфигурации с классами и передавать их через `IOptions`.
#### Сквозной сценарий задания 
Необходимо создать веб-приложение `CampusHub.ConfigCenter` которое играет роль учебного центра диагностики конфигурации внутреннего портала колледжа. Приложение должно показывать итоговые настройки портала демонстрировать объединение нескольких источников конфигурации, выводить структуру отдельных секций показывать строки подключения, использовать собственный провайдер конфигурации и передавать настройки в `middleware` через механизм `Options`.
#### Обязательные файлы и ключи конфигурации
| Файл | Назначение | Что должно лежать внутри | Примечание |
| - | - | - | - |
| appsettings.json  | Базовая конфигурация | Portal:Title, Portal:Semester, Portal:Admin:Name, Portal:Admin:Email, Portal:Modules, ConnectionStrings:DefaultConnection, FeatureFlags:* | Обязателен |
| appsettings.Development.json | Переопределение для Development  | Минимум два ключа, совпадающих с appsettings.json  | Обязателен |
| portal.xml  | Дополнительные настройки портала | Например: Portal:CampusName, Portal:Dean или Portal:Building | Обязателен |
| notifications.ini  | Настройки уведомлений  | Секция Notifications с Sender, Channel, Signature | Обязателен |
| customsettings.txt  | Файл для собственного провайдера  | Данные в формате: строка с ключом, следующая строка — значение | Обязателен |
| launchSettings.json  | Параметры запуска | ASPNETCORE_ENVIRONMENT, как минимум одна env var и commandLineArgs  | Обязателен |

**Рекомендуемый проверочный набор конфликтов ключей**: 
- `Portal:Title` должен существовать в 
`appsettings.json`, `appsettings.Development.json` и `commandLineArgs`; 
- `Portal:SupportEmail` — в 
`appsettings.json` и `environmentVariables`; 
- `Notifications:Sender` — в `notifications.ini` и `in-memory` коллекции. 
- На маршруте `/config/effective` студент должен показать финальные значения этих ключей. 

#### Обязательные маршруты и ожидаемое поведение
| Маршрут | Ожидаемое поведение | Какая тема проверяется |
| - | - | - |

| /config/raw | Возвращает несколько значений через `IConfiguration`: например `Portal:Title` `Portal:SupportEmail`, `Notifications:Sender`.  | Индексатор `IConfiguration` и `DI`  |
| /config/section/portal | Показывает данные секции `Portal` через `GetSection()`.  | `GetSection` |

#### Требования к порядку источников и демонстрации приоритета
- Студент должен осознанно показать, что конфигурация собирается из нескольких источников, а не хранится в одном `json-файле`. 
- Нужно продемонстрировать минимум два случая конфликта одинаковых ключей в разных источниках. 
- В отчете обязательно должно быть объяснение, какое значение победило и за счет какого источника или порядка подключения. 
- Маршрут `/config/providers` должен выводить реальные провайдеры, а не вручную написанный список строк. 
- Маршрут `/config/effective` должен показывать итоговые значения конфликтующих ключей, а не только их базовые значения из одного файла. 
- Для `portal.xml`, `notifications.ini` и `customsettings.txt` должно быть настроено копирование в выходной каталог приложения.





### CampusRouteLab
#### Цель работы
- Научиться создавать конечные точки `minimal API` методами `Map()`/`MapGet()` и связывать их с шаблонами маршрутов.
- Отработать обязательные, составные, необязательные, маршрутные параметры со значениями по умолчанию и `catch-all-параметры`.
- Закрепить регистрацию сервисов в `IServiceCollection` и показать различия между `Singleton`, `Scoped` и `Transient`.
- Корректно использовать сервисы внутри `custom middleware` и объяснять, почему `scoped-зависимости` нельзя помещать в конструктор `middleware`.

| Мартшрут | Что должно происходить | Формат ответа |

| /reports/{section?} | Маршрут с необязательным параметром. Если `section` не передан, использовать значение `overview`. | Текст или JSON |
| /portal/{module=home}/{page=index}/{id?} | Маршрут со значениями по умолчанию. В ответе явно показать, какие значения были получены системой маршрутизации. | Текст |

| /diag/request-services | Получить зависимость через `HttpContext.RequestServices.GetRequiredService(...)` и вывести результат. | Текст или JSON |

#### Сервисы и жизненный цикл зависимостей
| Сервис | Жизненный цикл | Назначение |
|-|-|-|
| IStudentCatalogService / StudentCatalogService | Singleton | Хранение и выдача тестовых данных о группах и студентах. |
| IAppInfoService / AppInfoService | Singleton | Идентификатор экземпляра приложения и время его запуска. |
| IRequestContextService / RequestContextService | Scoped | Идентификатор запроса и момент создания объекта на один HTTP-запрос. |
| ITransientMarkerService / TransientMarkerService | Transient | Новая метка/Guid при каждом разрешении зависимости. |

#### Требования к демонстрации жизненного цикла
- В endpoint-е `/diag/lifetimes` вывести значения `singleton`, `scoped` и `transient`, полученные напрямую из обработчика.
- В том же ответе вывести значения, полученные из `DiagnosticsReportService`, чтобы было видно, какие зависимости совпадают в рамках одного запроса.
- В endpoint-е `/diag/lifetimes/check` показать как минимум два разрешения `transient-сервиса` внутри одного запроса и явно зафиксировать, что значения различаются.
- В отчёте кратко пояснить разницу между `Singleton`, `Scoped` и `Transient` на основе результатов тестирования.

#### Обязательные способы получения зависимостей
| Способ | Где должен быть показан в работе |
|-|-|
| Через конструктор класса | В обычном сервисе, например в `DiagnosticsReportService`, который получает зависимости через конструктор. |
| Через параметр обработчика маршрута | В endpoint-ах `/students/{group}`, `/students/{group}/{id}` и `/diag/lifetimes`. |
| Через параметр InvokeAsync middleware | В `custom middleware` для `scoped/transient-сервисов`. |
| Через HttpContext.RequestServices | В endpoint-е `/diag/request-services` либо в отдельной диагностической ветке. |
| Через app.Services | Только для `singleton-сервиса` в `/diag app-services`. Использовать именно `GetRequiredService(...)`. |

#### Требования к custom middleware
- Создать класс `RequestAuditMiddleware` в отдельном файле и подключить его через метод расширения `UseRequestAudit()`.
- Через конструктор `middleware` получить `RequestDelegate` и `singleton-сервис` `IAppInfoService`.
- Через параметр метода `InvokeAsync` получить `IRequestContextService` и `ITransientMarkerService`.
- До вызова `next()` зафиксировать начало обработки запроса, после `next()` добавить в ответ диагностические заголовки `X-App-Instance`, `X-Request-Id` и `X-Transient-Id`.
- Для запросов в раздел `/diag` дополнительно вывести в консоль либо в ответ краткую информацию о способе разрешения зависимостей.





### StudentPortal
#### Какие темы и где отрабатываются
| Тема | Что реализует студент | Как проверить |
|-|-|-|
| Use() | Inline middleware, который замеряет время обработки запроса и записывает отметку до и после next. | В консоли или ответе видно, что код выполняется до и после следующего `middleware`.|
| UseWhen() | Ветка для запросов с `trace=true`: логирование и добавление заголовка `X-Debug-Trace`, затем возврат в основной pipeline. | Запрос `/tools/time?trace=true` обрабатывается веткой и затем обычным маршрутом. |
| MapWhen() | Отдельная ветка для `format=plain`, которая отдает специальный текстовый ответ и не продолжает основной pipeline. | Любой запрос с `format=plain` отрабатывает в отдельной ветке. |
| Map() | Ветка `/tools` и вложенные ветки `/tools/time`, `/tools/date`, `/tools/info`; отдельная ветка `/secure`. | Пути `/tools/*` и `/secure/*` работают независимо от основной ветки. |
| Классы middleware | `TokenMiddleware` и `ErrorHandlingMiddleware` как отдельные классы. | При неверном токене или неизвестном пути возвращаются ожидаемые статусы и сообщения. |
| Порядок pipeline | `ErrorHandlingMiddleware` должен стоять раньше остальных; токен-проверка должна выполняться раньше защищенного обработчика. | Студент в отчете объясняет, что изменится при перестановке компонентов. |
| IWebHostEnvironment | Endpoint `/env` показывает `EnvironmentName`, `ApplicationName`, `ContentRootPath`, `WebRootPath`. | При смене среды отображаются другие значения или меняется поведение ответа. |
| IServiceCollection и сервисы | Регистрация собственных сервисов и endpoint `/di/services` | В выводе видно наличие собственных и встроенных сервисов. |

#### Функциональные требования к приложению
1. Создать проект шаблона `Empty Web App под .NET 10`.
2. Настроить `inline middleware` через `app.Use(...)`, который делает две вещи: а) фиксирует момент начала обработки; б) после next добавляет запись о завершении обработки.
3. Создать ветку `UseWhen(...)`, которая срабатывает только если в `query string` есть `trace=true`. В этой ветке необходимо выполнить дополнительное логирование запроса и затем вернуть выполнение в основной pipeline.
4. Создать ветку `MapWhen(...)`, которая срабатывает при наличии `format=plain`. Ветка должна формировать самостоятельный текстовый ответ и не использовать основной маршрут.
5. Создать ветку `Map("/tools", ...)`, внутри которой должны быть вложенные маршруты `/tools/time`, `/tools/date` и `/tools/info`.
6. Создать ветку `Map("/secure", ...)`, в которой подключается custom middleware `TokenMiddleware` через собственный метод расширения `UseToke (...)`.
7. Реализовать `ErrorHandlingMiddleware`, который после выполнения следующих компонентов проверяет `StatusCode` и дописывает понятное сообщение для `403` и `404`.
8. Создать endpoint `/env` с выводом данных из `IWebHostEnvironment`.
9. Создать endpoint `/di/services`, который показывает хотя бы общее число сервисов и не менее 10 записей из `builder.Services`.
10. Зарегистрировать минимум два собственных сервиса и вынести их регистрацию в метод расширения `AddStudentPortalServices(...)`.

#### Обязательные маршруты и ожидаемое поведение
| Запрос | Ожидаемое поведение | Какая тема проверяется |
|-|-|-|
| / | Стартовая страница приложения. Краткое описание проекта и ссылки на тестовые маршруты. | Терминальный обработчик |
| /tools/time | Возвращает текущее время через сервис. | Map + DI |
| /tools/date | Возвращает текущую дату через сервис. | Map + DI |
| /tools/info | Отдает краткую диагностическую информацию о приложении. | Вложенные ветки Map |
| /tools/time?trace=true | Сначала выполняется ветка `UseWhen`, затем основной обработчик `/tools/time`. | UseWhen |
| /anything?format=plain | Запрос должен быть перехвачен отдельной веткой и вернуть plain-text ответ. | MapWhen |
| /secure/report | Без токена должен вернуть `403` и текст ошибки. | Класс middleware |
| /secure/report?token=study2026 | При валидном токене доступ разрешен. | Класс middleware + extension |
| /env | Показывает сведения об окружении и путях приложения. | IWebHostEnvironment |
| /di/services | Выводит сведения о сервисах из `IServiceCollection`. | IServiceCollection |
| /unknown | Возвращает `404` и сообщение `Not Found`. | Порядок pipeline + ErrorHandlingMiddleware |    

#### Порядок pipeline + ErrorHandlingMiddleware
- `ErrorHandlingMiddleware` должен стоять первым, чтобы видеть результат работы следующих компонентов и корректно реагировать на `403` и `404`.
- `Inline middleware` на `Use()` должен находиться до основных ветвей, чтобы оборачивать их выполнение.
- `UseWhen(...)` должен только расширять обработку и возвращать запрос в основной pipeline.
- `MapWhen(...)` должен отделять запросы особого формата в самостоятельную ветку.
- Ветка `/secure` должна включать токен-проверку раньше терминального обработчика защищенного ресурса.
- Нельзя одновременно бездумно писать ответ через `Response.WriteAsyn (...)` и затем продолжать `next`, если это ломает логику ответа.





### TaskManager
#### Цель работы
Изучить основы разработки backend‑приложений на платформе `.NET` с
использованием `ASP.NET Core Minimal API.`
В ходе работы необходимо разработать `REST API` для управления списком
задач.
В данной работе база данных не используется.
Все данные должны храниться в JSON файле на сервере.
#### Описание задачи
Необходимо реализовать `REST API "Менеджер задач" (Task Manager API)`.
Система должна позволять:
- получать список задач
- получать конкретную задачу
- создавать новую задачу
- изменять задачу
- удалять задачу

Все данные должны сохраняться в JSON‑файле.

#### Требуемые API endpoints
1. Получить список всех задач <br/>
`GET /api/tasks`

Пример ответа:
```properties
[
   {
      "id": 1,
      "title": "Сделать практичку",
      "description": "ASP.NET Core API",
      "isCompleted": false
   }
]
```

2. Получить задачу по ID <br/>
`GET /api/tasks/{id}`<br/>
Если задача не найдена - вернуть:<br/>
`404 Not Found`<br/>

3. Создать новую задачу<br/>
`POST /api/tasks`

Тело запроса:
```properties
{
   "title": "Изучить ASP.NET Core",
   "description": "Minimal API"
}
```
Сервер должен:
- создать новую задачу
- автоматически сгенерировать Id
- сохранить задачу в JSON файл

4. Обновить задачу<br/>
`PUT /api/tasks/{id}`
```properties
{
   "title": "Изучить ASP.NET Core",
   "description": "Minimal API и Swagger",
   "isCompleted": true
}
```

5. Удалить задачу<br/>
`DELETE /api/tasks/{id}`<br/>
После удаления задача должна исчезнуть из JSON файла.

#### Требования к реализации
В проекте должны быть реализованы:
- модель данных
- JSON файл для хранения данных
- endpoints для CRUD операций
- использование Minimal API
- тестирование API через Swagger
